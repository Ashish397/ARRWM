## The stationary table — retracted and re-traced

Tracing against the per-rollout files rather than the aggregate:

**Relocation reproduces**: `noop_cpu.drift_inl < 59` gives twelve of thirteen
published figures exactly. **Geometry is close**: `noop_vlm.p_imp > 0.3` gives
ten of thirteen, with Matrix-Game 94/94, WorldPlay 16/16, WorldCam 19/19.
**Style, conjuration and HF are not traced** — the best style candidate reaches
seven of thirteen.

The one relocation miss is Astra, 41 against the published 31, and there is a
documented reason: `stationary_evaluation_replace/MANIFEST.csv` holds exactly
Yume and Astra, 32 scenes each, annotated *"neutral prompt: dropped 'The camera
moves smoothly through the scene.'"* — matching the paper's statement about
neutral prompts for those two. The neutral videos are the one stationary set not
on this machine, so I cannot close it. Scoring `A_astra_noop_neutral` and
checking whether `drift_inl < 59` yields 31% would settle it in one run.

**A generation detail that matters**: `noop_*` and `stationary_*` are different
generations. `noop_cpu` expects `grids/noop/<model>_rNN_noop.mp4`;
`stationary_*` expect `~/stationary_evaluation/<model>_rNN.mp4`, which is the
current set and was re-rendered on 30 July. My traces above are against the
older `noop_*` results, so they establish those rules for that generation, not
necessarily for the current videos.

So: removing the `noop_*` tree is defensible for relocation and geometry, not
established for the other three. I would not restore it on this evidence, nor
call the stationary table verified.

## Running a new ablation exposed five instrument defects

Adding one model is a good stress test, because every instrument has to resolve
a variant that did not exist when the grid was built. None of these would appear
from reading the code, and none is caught by reproducing the paper's numbers,
because the reference CSVs already contain the answers.

- `fleet_common` could only reach our variants by de-tiling the grid, so any
  model trained afterwards was unreachable.
- `popin_fleet_all` raised `KeyError` on the unknown variant and **skipped all
  256 rollouts while still reporting a completed run** — the worst kind.
- `vlm_external` needed `gt.json`, which was not shipped, so it could not start;
  and it re-scored all fourteen models when asked for one.
- `fleet_static_inl` and `scene_consensus` hardcoded the seven known ablations.
- `fleet_hf` had its progress total hardcoded to 3328, so a 448-rollout
  stationary run appeared to be scoring the wrong set.

An undocumented field detail: raw renders are 832x480, grid tiles are 832x448,
because de-tiling drops the top 32 rows — which carry a burned-in model label. A
new ablation must be cropped identically or it is compared at a different field
of view. I found that only by diffing frame shapes.

## Two hazards

**Reference artefacts are overwritten by default.** Three instruments wrote a
shipped artefact backing a published number as their default output, and all
three did it here in one session while I evaluated a single ablation:
`vlm_external` appended twelve rows to `results_external_vlm.csv`,
`scene_consensus` overwrote `fleet_scene_consensus.csv`, and `fleet_static_inl`
would have done the same. Each was caught by a row-count or reproduction
assertion and restored from git. All now take an explicit output path.

**The figure-label divergence is unresolved and I think it is the release
blocker.** The scripts currently in `code_release/figures/` are your refactor
onto the shared label module, which changes rendered text — "batch size 16"
becomes "batch 16", "pca8" becomes "Default". I reverted them to the workstation
versions because those rendered the submitted figures; the merge overwrote my
revert and I did not re-check until now. So as it stands, a reviewer running the
released figure code gets legends that do not match the paper.

Your consolidation is the better long-term answer, and the paper's labels are
inconsistent across figures today. But that is a camera-ready decision, not one
to make silently in the release. **Which version is authoritative?** If the
figures are being re-rendered for camera-ready, yours is right and the paper
changes with it. If not, the workstation versions need restoring.

## New: the no-critic ablation

Scored over the standard 256-rollout benchmark with the same frozen instruments.
Results and per-rollout data are committed under `analysis/nocritic_ablation/`.

| axis | no-critic | Default |
|---|---|---|
| geometric corruption | 1.6% | 16.8% |
| scene relocation | 10.9% | 10.9% |
| style shift | 0.0% | 2.5% |
| high-frequency degradation | 16.3% | 27.2% |
| conjuration | 0.4% | 1.2% |
| control failure | **77.3%** | 0.4% |
| legitimate | **17.2%** | 73% |
| active population | **92** | 239 |

It wins or ties four of five quality axes and fails control almost entirely,
because 64% of its rollouts are near-static. Realised throttle spread across the
eight commands is 0.072 against Default's 0.652; steering reads -0.003 on L and
+0.003 on R against -0.685 and +0.674.

Worth knowing on your side: this is a sharper demonstration of the paper's own
argument than any baseline, being a single-variable change that tops the quality
table and bottoms the legitimacy one. Relocation identical to Default says the
ablation severed command from output without damaging generation.
